# Internal recording storyboards — retained, not public copy

20 October 2026. Product Overview is the single public product page. These briefs preserve the useful former Product Experience recording plans; none is a captured or approved video. They are not emitted to the runtime or linked from public navigation. No WMS certification or application change was launched for this release.

## Stock investigation

Context: a supervisor investigates stock in a location. Goal: identify the stock identity and understand its displayed hold/balance state.

1. Locate the owner, SKU, location and relevant lot/container.
2. Inspect the displayed hold context.
3. Find the matching operation and verify the readback explains the balance.

Evidence: supplied inventory and transaction views plus source paths in the existing capability matrix. Dependency: same coherent case/build, matched readback and approved sample data/recording. Separate still images do not establish a connected workflow. No blanket hold-policy or permission acceptance claim.

## Allocation top-up

Context: an order has a partial allocation. Goal: show what a further normal allocation changes.

1. Show the starting demand and reservation state from the retained scenario.
2. Invoke the exact accepted normal top-up path.
3. Read back the reservation and remaining demand.

Internal evidence reference: TOPUP-01 scoped normal API PASS at product d105fce52; Allocation remains NOT Certified in that record. This is not evidence for picking, shipping, every allocation strategy or throughput. Dependency: selected accepted build/policy and an actual usable UI. Do not substitute a fictitious operator screen for an API test. A technical walkthrough would need accurate labelling and separate approval.

## Supported configuration change

Context: one warehouse process needs a supported configuration change. Goal: explain before/after behaviour and ownership.

1. Before: capture the original operation, configuration version and expected difference.
2. Change: show one supported setting, its validation and actual activation.
3. After: repeat the same operation/data, compare the expected result, and show restoration only if supported and verified.

Dependency: no complete selected before/after acceptance evidence has been approved in this website workstream. ACTION FOR AGENT: identify one existing supported change and applicable evidence; do not invent a metadata entity/API. No automatic configuration, zero-code coverage, time-to-go-live or cost-saving promise.

## Receipt into storage — later candidate

1. Show accepted receipt quantity and identity.

Dependency: existing applicable receiving retests and putaway acceptance tied to the chosen build. Historical bounded receiving passes are not a complete inbound or receive-to-ship certification. Expected fixes are dependencies, not completed QA. Defer rather than starting a fresh full certification for media.
